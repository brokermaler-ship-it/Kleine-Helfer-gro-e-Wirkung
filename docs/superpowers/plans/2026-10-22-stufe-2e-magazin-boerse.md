# Teil 2e – Magazin und Modellbahnbörse – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Magazin als Inventarliste des Vereins mit unveränderlichen Buchungen (Eingang, Ausgang, Umlagerung) und Code `M<n>`, Übergabe ausgemusterter Fahrzeuge ans Magazin, Modellbahnbörse intern (Angebote von Verein und Mitgliedern, Freigabe, Preisschilder), Kasse am Handy ohne Doppelverkauf, Abrechnung und Abschluss je Börse sowie ein abschaltbarer öffentlicher Bereich `/boerse` mit Kaufanfrage und „Sammlung anbieten“.

**Architecture:** Zwei neue Namensräume nach dem Muster von `Emc\Reparatur`: `Emc\Magazin` (Repository nur SQL, `MagazinDienst` für alle Bestandsbuchungen in Transaktionen) und `Emc\Boerse` (Repositories, `AngebotDienst`, `KasseDienst`, `BoerseDienst`, `AnfrageDienst` für Transaktionen; reine, voll unit-testbare Bausteine `Geld`, `Angebotsnummer`, `Freigabe`, `Abrechnung`, `Spamschutz`). Der Bestand wird nie gespeichert, sondern immer als `SUM(menge)` der Buchungen gelesen – nach Sperre des Artikels. Fotos hängen über `dokument_zuordnung` (`magazin_artikel`, `boerse_angebot`, `boerse_anfrage`); der öffentliche Bereich liefert nur die GD-erzeugten Anzeige-Varianten aus und speichert öffentliche Uploads nur neu kodiert (ohne EXIF/GPS).

**Tech Stack:** PHP 8.2, PDO/MariaDB 10.6+/MySQL 8, PHPUnit 11, bestehendes Template-System (`View`, `e()`, `url()`), Bootstrap 5, GD, bestehende `Emc\Etiketten\Bogen`/`QrCode` (chillerlan/php-qrcode), Druck-CSS. Keine neue Composer-Abhängigkeit.

**Spec:** `docs/superpowers/specs/2026-10-20-magazin-modellbahnboerse-design.md` (alle Abschnitte 1–9); Rollen aus `docs/superpowers/specs/2026-10-20-stufe-2-wartung-reparatur-design.md` §3; Hauptspezifikation `docs/superpowers/specs/2026-10-18-emc78-fahrzeug-anlagen-verwaltung-design.md`.

## Global Constraints

- PHP ≥ 8.2, kein Framework; SQL muss auf MariaDB ≥ 10.6 **und** MySQL ≥ 8 laufen. Keine neue Composer-Abhängigkeit.
- Neue Migrationen `016_magazin.sql` (Task 1), `017_boerse.sql` (Task 4), `018_boerse_anfrage.sql` (Task 7); 001–015 nicht ändern. `MigratorTest` (Versionslisten) je Task ergänzen.
- Ränge: Mitglied 1, Fahrzeugwart 2, Bearbeiter 3, Admin 4. **Börsenwart** ist das Häkchen `benutzer.ist_boersenwart`, unabhängig von der Rolle; Bearbeiter und Admin dürfen alles, was der Börsenwart darf (`Berechtigung::istBoersenwart`). Ein Fahrzeugwart ohne Häkchen ist **kein** Börsenwart.
- **Jede Schreibung, die Bestand oder Status ändert** (Buchung, Gegenbuchung, Übergabe, Angebot aus Magazin, Kasse, Storno, Abschluss, Anfrage anlegen), läuft in **einer** Transaktion mit `READ COMMITTED` über `Emc\Core\Transaktion::readCommitted` (Muster `ReparaturDienst::inTransaktion`) und sperrt zuerst das Elternobjekt mit `SELECT … FOR UPDATE`. Feste Sperrreihenfolge app-weit: `boerse` → `boerse_angebot` (nach id aufsteigend) → `magazin_sammlung` → `magazin_artikel` (nach id aufsteigend) bzw. `fahrzeug` → `magazin_artikel`. Sperrkonflikte (1205/1213) → `DomainFehler` „Gerade arbeitet jemand anderes daran. Bitte noch einmal versuchen.“, nichts gespeichert, nie 500.
- **Geld:** Spalten `DECIMAL(10,2)`, in PHP nur als Zeichenkette (`"12.50"`) oder ganze Cent (`int`) über `Emc\Boerse\Geld` – **nie `float`**, kein `round()`/`number_format()` auf Beträgen. Eingabe wie bisher über `ReparaturValidator::betragWert` (`12,5` → `12.50`; Fehlertext „Bitte den Betrag angeben, z. B. 12,50.“), Anzeige über `ReparaturValidator::betrag` (`12,50 €`). Summen in SQL oder in Cent.
- **Bestand** = `SUM(magazin_buchung.menge)` (Eingang positiv, Ausgang negativ, Umlagerung 0), nie als Spalte gespeichert, nie negativ. Buchungen sind unveränderlich; Korrektur nur per Gegenbuchung. Magazinartikel und Buchungen werden nicht gelöscht (keine Löschroute).
- **Uploads** nur über `UploadService` mit den bestehenden `Uploadgrenzen` und `templates/partials/fotofeld.php` (clientseitige Verkleinerung in `public/assets/app.js`). **Öffentliche Uploads** kommen auch ohne JavaScript an: sie werden serverseitig mit GD neu kodiert (`Bildbearbeitung::ohneMetadaten`), das Original mit EXIF/GPS wird nie gespeichert; was GD nicht lesen kann, wird abgelehnt. Fotos von `boerse_anfrage` gehen nie nach OneDrive.
- **Öffentlicher Bereich** (`/boerse` und `/boerse/…`, **nicht** `/boersen…`): nur aktiv bei `boerse_oeffentlich === true` **und** nicht leerer `datenschutz_url` (`https://…`), sonst 404. Vor dem Datenbank-Update 503-Wartungsseite. Kein Personenname, keine Herkunft Verein/Mitglied, keine Notiz, kein Magazin-Code, kein Lagerort, kein Originaldateiname im HTML oder in Headern. Fotos nur als Anzeige-/Vorschau-Variante. Alle POST mit CSRF (globaler Schutz in `App`). Fangfeld/zu schnell → identische Dankeseite ohne Speichern; Begrenzung 5 je Stunde und IP mit `hash_hmac('sha256', REMOTE_ADDR, salz)` (Muster `KennwortVergessen`, eigenes Salz `boerse_ip_salz`), Sperrzeilen nach 24 h gelöscht.
- Pfade, die Tabellen aus 016–018 brauchen, stehen in `App::brauchtNeuesSchema` (`/magazin`, `/angebote`, `/boersen`, `/kasse`, `/verkaeufe`, `/anfragen`, `/admin/magazin-kategorien`); Blöcke auf bestehenden Seiten (Fahrzeugseite, Hinweise) fangen SQLSTATE `42S02`/`42S22` ab. `Auth::benutzer` liest `ist_boersenwart` mit `?? 0` (vor 016 fehlt die Spalte).
- Gleichzeitige Bearbeitung über den bestehenden Stand-Schutz (`geaendert_am DATETIME(6)`, Feld `stand`, `KonfliktFehler` → 409) bei Artikel, Sammlung, Angebot und Börse.

## Review Focus

1. **Doppelverkauf und negativer Bestand unter Gleichzeitigkeit:** Zwei Kassen haben dasselbe Stück im Warenkorb und schließen gleichzeitig ab → genau ein Verkauf, die zweite bekommt „B2026-118 ist bereits verkauft.“ und **keine** ihrer Positionen ist verkauft; Kasse und „Börse abschließen“ gleichzeitig; zwei Ausgänge gleichzeitig über einen Bestand von 1; ein Artikel steckt in einer Sammlung **und** in einem Einzelangebot. → Tests in Task 2 (`test_gleichzeitiger_ausgang`), Task 5 (`test_gleichzeitige_kassen_prozess`), Task 6 (`test_abschluss_wartet_auf_kasse`).
2. **Interne oder personenbezogene Daten im öffentlichen Bereich:** Name der Person, Notiz, Lagerort, `M<n>`, „Mitglied“/„Verein“ als Herkunft, Originaldateiname (`Content-Disposition`), Original-Foto statt Variante; nicht freigegebene, verkaufte und zurückgegebene Angebote antworten wie unbekannte Nummern (404); `/boersen` und `/boersen/1/kasse` bleiben hinter der Anmeldung (Präfix-Falle `/boerse` vs. `/boersen`). → Tests in Task 7.
3. **Öffentliche Formulare ohne JavaScript und von Bots:** JPEG mit GPS-EXIF direkt hochgeladen → gespeicherte Datei ohne EXIF; HEIC/PDF → Meldung, Anfrage trotzdem gespeichert; Fangfeld gefüllt oder < 3 s → dieselbe Dankeseite, nichts gespeichert, nicht gezählt; 6. Anfrage in einer Stunde → „Bitte später erneut versuchen.“; `boerse_oeffentlich = 'true'` (Zeichenkette) oder fehlende `datenschutz_url` → 404. → Tests in Task 7.
4. **Cent-genaue Abrechnung:** Provision je Stück kaufmännisch (12,50 € bei 10 % → 1,25 €; 0,05 € → 0,01 €; 0,04 € → 0,00 €; 3,35 € bei 15 % → 0,50 €), 0 % und 100 %, Spende → Auszahlung 0 €; Summe der Zahlarten = Verein + Provisionen + Spenden + Auszahlungen; stornierte Verkäufe zählen nicht; Provision lässt sich nach dem ersten Verkauf nicht mehr ändern. → Tests in Task 4 (`GeldTest`) und Task 6.
5. **Rechte und Zustände:** Fahrzeugwart ohne Häkchen bucht nicht (403), Mitglied mit Häkchen schon; Mitglied ändert fremdes Angebot (403); Änderung eines freigegebenen Angebots durch das Mitglied → `vorgeschlagen`, durch den Börsenwart nicht; abgeschlossene Börse: Kasse, Storno und Angebotsänderung abgelehnt, nur Admin öffnet wieder; Storno am Folgetag abgelehnt; Datenbank vor 016: Anmelden und Startseite funktionieren. → Tests in Task 1, 4, 5, 6.
